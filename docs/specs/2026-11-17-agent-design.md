# 審査支援エージェントとトレースの可視化

- 日付：2026-11-17
- 前提：`docs/specs/2026-11-16-ontology-design.md`（オントロジーの段。PR #2 でマージ済み）。この仕様はその「ゴールにしないこと」に挙げた「エージェント本体、トレースの JSON スキーマ、報告の形」を決める。
- 対象：オントロジーを使う審査支援エージェント、ツール、トレースの記録、ローカルの Web 画面での可視化。
- 追記（2026-11-19）：モジュールの置き場所（`src/semantica_agent/agent/` 等）、`ReviewSession`、トレースの `runtime`、Claude Code 版は `docs/specs/2026-11-19-package-split-and-claude-code.md` を参照。この仕様に出てくるファイル名は当時のもの。

## 1. 目的

窓口職員が日本語で質問すると、エージェントがオントロジーへのツール呼び出しで答える。そのとき **AI がどう処理したか** を、手順書のフローの上で「どこを通ったか」に色を付けて見せる。プロジェクト全体の目的（オントロジーを持たせることが役に立つかの検証、特にトレーサビリティ）のうち、この段は「結論から根拠まで辿れること」を目で見て確かめられるようにする。

### 想定する質問（ユーザーの決定：両方を扱い、A を主にする）

- **A. 事案の審査（主）**：「4月1日生まれ、婚姻から150日、父が非本籍地で届出。受理できる？」。エージェントは文章を出生届の事案データに直し、判定ルール（SHACL）で判定して、受理可否・不足・照会の要否を根拠付きで返す。
- **B. 手順・法令の問い合わせ**：「待婚期間の審査は今も要る？」「戸籍法施行規則第48条が関わる工程は？」。エージェントはオントロジーを SPARQL などで引いて答える。

### ゴール

- ローカルの Web 画面で、質問の入力・回答・フローの色付け・ノードの詳細を見られる。
- エージェントは Claude Agent SDK で作り、オントロジーへの問い合わせはカスタムツールとして渡す。LLM の知識だけで判定させない。
- 1 回の質問ごとに、入力 → 呼んだツールと引数 → 参照したノード → 適用したルールと判定 → 結論 をトレースとして JSON に残す。記録はコード（ツールの実装と SDK のフック）が行い、LLM の自己申告に頼らない。
- 回答の各主張に、根拠の種類（オントロジーの事実／ルールの判定／LLM の推測）と根拠のノードを付ける。種類はコードが確かめる。
- 保存したトレースを画面で開き直すと、同じ図を再生できる。

### ゴールにしないこと

- 「LLM＋手順書の文章」との比較評価（次の仕様で行う。トレースの形式はそこで再利用できるようにしておく）。
- 出生届以外の判定ルール。他の 4 業務は B の問い合わせ（フローへの色付けを含む）だけを扱う。
- 複数人での利用、認証、外部への公開、スマートフォンの画面。Pro のログインで動かすので、自分のマシンで自分が使う範囲に限る。
- 子の名に使える文字の判定、住所・戸籍の実在の照合（オントロジーの仕様と同じく、人の確認事項か入力値として扱う）。

### 失敗とみなすこと（動いても失敗）

- フローの色が、ツールの実行結果ではなく LLM の申告や回答の文章から決まっている。
- 届出の内容を事案データに直すとき、職員が言っていない値を黙って補い、それが画面で区別できない。
- 入力が欠けて評価できなかったルールの審査項目が「通過」と表示される。
- 根拠のノードを示せない主張が、事実やルールの判定として表示される。
- 保存したトレースから再生した図が、その場で見た図と違う。

## 2. 進め方の選択（Approaches）

| 案            | 内容                                                                | 長所                                                                               | 短所                                                     |
| ------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------- |
| **1（採用）** | ローカルの Web 画面。左で質問と回答、右で手順書のフローに色を付ける | 処理が進むのに合わせて、通ったところに色が付いていくのを見られる。続けて質問できる | サーバーと画面のコードが要る                             |
| 2             | コマンドラインで質問し、色付きのフロー図を HTML の報告に出す        | サーバーが要らず最小                                                               | 終わってからしか見えない。続けての対話がしにくい         |
| 3             | Streamlit などの画面部品                                            | 画面を早く作れる                                                                   | フローの色付けと途中の更新を作り込みにくい。依存が増える |

**案 1 を採用**（ユーザーの決定）。どの案でも、トレースを JSON に残して画面はそれを描くだけにする、という作りは共通にする。

## 3. 全体の構成

```
ブラウザ（127.0.0.1）
  │ 質問（POST）／処理の進み（Server-Sent Events）
  ▼
web.py（FastAPI）── セッションごとに Agent（ClaudeSDKClient）を持つ
  │                     │ カスタムツール（SDK 内の MCP サーバー）
  │                     ▼
  │                tools.py ── judge.py / オントロジー（rdflib の Graph、起動時に 1 回読む）
  │                     │
  │                     └─ 記録 ─▶ trace.py（イベントを積む → フローの状態を計算）
  ▼
output/traces/<session_id>/<turn>.json（＋ report.md、semantica の ContextGraph、PROV-O）
```

- オントロジー（`ontology/` の全ファイルと `rules/birth-rules.ttl`）は起動時に 1 回読み、整合性シェイプで検証してから使う。検証が通らなければ起動を止める。
- 新しく作るモジュール（目安）：`agent.py`（SDK の組み立てと会話）、`tools.py`（ツール）、`case_input.py`（事案データへの変換と引用の照合）、`claims.py`（主張の検証）、`flow.py`（フローの形と状態）、`trace.py`（記録と保存）、`web.py`（サーバー）、`web/static/`（HTML・JS・CSS）、`prompts/agent.md`（システムプロンプト）。
- 依存に `fastapi` と `uvicorn` を足す（設計者の判断）。画面は素の HTML・JS・CSS で書き、外部の CDN を読まない（ローカルで閉じて動かすため）。フロー図は工程が一列に並び、その下に項目が入れ子になる形なので、グラフ描画のライブラリは使わず HTML と CSS で描く（設計者の判断）。

## 4. エージェント

### 4.1 SDK の使い方

- `ClaudeSDKClient` を 1 つの相談（セッション）ごとに作り、続けての質問は同じクライアントに送る。画面の「新しい相談」で作り直す。
- `ClaudeAgentOptions`：
  - `mcp_servers` に `create_sdk_mcp_server` で作ったツールのサーバーを渡す。`allowed_tools` はそのツールだけにし、組み込みのツール（ファイル操作、シェル、Web）は使わせない（`tools=[]`）。
  - `setting_sources` を空にし、このリポジトリの `CLAUDE.md` や設定を読み込ませない。
  - `system_prompt` は `src/semantica_agent/prompts/agent.md` を読み、ハッシュをトレースに残す。今日の日付をプロンプトに差し込む（「今日届けた」の解釈に要るため）。
  - `max_turns` は設定にする（既定 20）。
  - `hooks` に `PreToolUse` と `PostToolUse` を付け、ツールの呼び出しの時刻・引数・結果をトレースに積む。
- モデルは環境変数 `AGENT_MODEL`（未設定なら設定ファイルの既定値 `claude-sonnet-5-5`。設計者の判断で、生成の段と同じにする）。応答したモデル名はメッセージから取ってトレースに残す。
- `ANTHROPIC_API_KEY` があれば起動時に止める（既存の `load_settings` を使う）。

### 4.2 システムプロンプトの中身（`prompts/agent.md`）

1. 役割：戸籍の窓口職員の審査を支援する。判定はツールの結果からだけ導く。
1. 事案の審査：届出の内容は `judge_birth_case` に渡す。職員が言っていない項目は未確認（`unknown`）のままにし、値を入れない。「無い」と言われた項目だけ `none` にする。計算で補った値には `inferred` を付ける。判定保留なら、未確認の項目を職員に聞き返す。
1. 問い合わせ：`search_nodes`・`describe_node`・`run_cq`・`run_sparql` で引く。
1. 回答は必ず `submit_answer` で出す。主張ごとに根拠の種類とノードの短い ID を付ける。ツールで確かめていないことは「推測」にする。
1. 未承認の現行版に基づく指摘（暫定）と、手順書と現行で結論が違うこと（B4c）は、そうと分かるように書く。

文面は実装に任せる（§10）。

## 5. ツール

ツールの結果は、ノードを短い ID（`dcterms:identifier`）とラベルで返す。どのツールも、結果に出てきたノードを「参照したノード」としてトレースに積む（ツールの実装側で行う）。

| ツール             | 入力                                 | 出力                                                                                                                                   | 用途 |
| ------------------ | ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- | ---- |
| `judge_birth_case` | 出生届の事案の各項目（§5.1）         | 判定（§5.1.1）、未確認の項目、評価できなかったルール、暫定の判定、指摘の一覧（ルール・判定の種類・審査項目・条文の版・メッセージ・値） | A    |
| `search_nodes`     | 文字列、業務（任意）、クラス（任意） | ラベルに一致するノード（短い ID・ラベル・クラス・業務）。最大 20 件                                                                    | A・B |
| `describe_node`    | 短い ID                              | ラベル、クラス、属する業務・工程、親子の項目、適用条件、書類、条文、条文の版と現行の扱い、ルール、出典                                 | A・B |
| `run_cq`           | CQ の番号（1〜15）                   | `ontology/cq/cqNN.rq` の結果（行ごと、IRI は短い ID に直す）。番号の一覧と問いの文はツールの説明に書く                                 | B    |
| `run_sparql`       | SELECT の SPARQL                     | 結果の行（最大 200 行、IRI は短い ID に直す）。SELECT 以外と、`SERVICE` を含む問い合わせは拒む                                         | B    |
| `submit_answer`    | 回答の本文と主張の一覧（§5.2）       | 検証した結果（主張ごとの種類の確定）                                                                                                   | 共通 |

### 5.1 事案データへの変換（`judge_birth_case`）

- 入力の JSON スキーマは、オントロジーの仕様 §4.4 の事案側のプロパティに合わせる（出生日、届出日、届出地、本籍地、出生地、届出人の所在地、届出人の資格、添付書類、記載事項、続き柄、届書上の父、出生証明書の日時・場所、母の生年月日、婚姻日、前婚の解消日、再婚の有無、戸籍・住所の存在）。資格・書類・記載事項は列挙値（オントロジーの個体の短い ID）で受け取る。列挙値の一覧は、起動時にオントロジーから作ってスキーマに入れる。
- 各項目は 3 つの状態のどれかで受け取る（ユーザーの決定：未確認と「無い」を分ける）。
  - `given`（値がある）：`{status: "given", value, quote, inferred, note}`。
  - `none`（無いと確認した）：`{status: "none", quote}`。例：「出生証明書はありません」「前婚はありません」。
  - `unknown`（未確認）：項目を省くか `{status: "unknown"}`。職員が触れていない項目はすべてこれになる。
  - 複数の値をとる項目（添付書類、記載事項）は、`{items: [...], complete}` で受け取る。`complete: true`（「添付はこれだけ」と確認した。引用が要る）のときだけ、一覧に無いものを「無い」とみなす。`complete: false` なら、一覧に無いものは未確認。
- `quote`：その値の根拠になった職員の発言の一部。コードが、この相談の職員の発言（全ターン）に空白を除いて含まれるかを照合する。含まれなければツールはエラーを返し、どの項目かを示す（LLM は直すか、職員に聞き返す）。
- `inferred: true`：発言から計算・解釈して補った値（「婚姻から150日」から逆算した婚姻日、「今日」から決めた届出日など）。このときは `quote` に計算の元になった発言を入れ、`note` に補い方を書く。
- コードが事案の RDF（`kcase:<session_id>-<turn>`）を組み立て、`judge()` を呼ぶ。`given` だけを三つ組にし、`none` と `unknown` はどちらも三つ組を作らない（ルールとオントロジーは変えない）。組み立てた事案の Turtle と、項目ごとの「状態・値・引用・推測かどうか」の表をトレースに残し、画面に「入力の解釈」として出す。

### 5.1.1 未確認の項目と判定の後処理

`judge()` は値が無いことを「無い」と読むので、未確認の項目があると誤った指摘や見かけの「通過」が出る。これを判定の後処理で補う（ユーザーの決定）。

- 各ルールの「使う入力」（§7.2 の洗い出し）に、未確認の項目が 1 つでも入っていれば、そのルールは**評価できず**とする。そのルールの指摘は判定に数えず、「評価できなかったルール」として、どの未確認の項目のせいかと一緒に返す。指摘が出ていなくても、そのルールの審査項目は「通過」にしない。
- 既存の `judge()` の `missing_inputs`（`BIRTH_REQUIRED_INPUTS`）は、未確認の項目に含めて扱う（`none` と答えられない必須の項目も、値が無ければ未確認とみなす）。
- 全体の判定（コードが決める）：
  - 評価できたルールに受理不可・補正・照会・追加の手続の指摘があれば、最も重いもの（既存の `SEVERITY_ORDER`）。未確認の項目が残っていれば「（ほかに未確認あり）」を添える。
  - 指摘が無く、評価できなかったルールがあれば **判定保留**。未確認の項目の一覧を付ける。受理できるとは言わない。
  - 指摘が無く、すべてのルールを評価できたときだけ **受理可**。
- エージェントは判定保留のとき、未確認の項目を職員に聞き返す（§4.2）。
- 回答の画面では、この判定を LLM の本文とは別に、コードの結果として上部に出す。LLM の本文が判定と食い違って見えても、判定の表示はコードの結果を正とする。
- 同じ相談の中で職員が情報を足したら、エージェントはまとめ直した全項目でもう一度呼ぶ。判定は呼ぶたびに独立に行い、どの呼び出しの判定を回答に使ったかはトレースで分かるようにする（最後の呼び出しを画面に出す）。

### 5.2 回答と主張の検証（`submit_answer`）

- 入力：`answer`（本文）、`claims`：`[{text, kind, nodes}]`。`kind` は `fact`（オントロジーの事実）・`rule`（ルールの判定）・`speculation`（推測）。
- コードの検証：
  - `nodes` の短い ID がオントロジーに無ければ、その ID を外す。
  - `rule`：この相談の最後の `judge_birth_case` の結果に、`nodes` のどれかをルールまたは審査項目とする指摘があること。無ければ `speculation` に下げる。
  - `fact`：`nodes` のどれかが、このターンのツールの結果に出てきたノード（参照したノード）であること。無ければ `speculation` に下げる。
  - 下げたときは理由をトレースに残し、画面で「推測（根拠の確認ができなかった）」と出す。
- `submit_answer` が呼ばれずにターンが終わったら、最後の文章を回答とし、主張は全体を 1 つの `speculation` として扱う。

## 6. トレース

### 6.1 記録の仕方

- 1 回の質問（ターン）ごとに 1 つのトレースを作る。記録はコードが行う：
  - 職員の発言、LLM の文章（`TextBlock`）、ツールの呼び出しと結果（フック）、判定の結果、回答と主張の検証。
  - 各ツールの結果から、そのイベントで触れたノードと、ノードの状態（§7.2）をコードが決めて積む。
- LLM の思考（`ThinkingBlock`）は記録するが、画面では折りたたんで出す（設計者の判断。検証の材料にはなるが、根拠ではないため）。
- 保存先：`output/traces/<session_id>/<turn:03d>.json`（git 管理外）。同じ場所に人が読む `report.md` を書く。
- semantica の判断記録：判定ごとに `ContextGraph.record_decision` を呼び、`ContextGraph` をセッションのフォルダに保存する。引数はすべてコードが作り、LLM の文章は使わない（設計者の判断）：category＝出生届の判定、scenario＝事案の IRI と出生日、reasoning＝指摘・評価できなかったルールの一覧を文にしたもの、outcome＝§5.1.1 の判定、confidence＝未確認の項目が無く暫定の指摘も無ければ 1.0、それ以外は 0.5、entities＝指摘のルール・審査項目の IRI、metadata＝トレースのパス。
- PROV-O：ターンを `prov:Activity` にし、`prov:used`（参照したノード、事案、オントロジーのコミット）、`prov:wasAssociatedWith`（モデル）、生成した判定を Turtle でセッションのフォルダに書く。

### 6.2 トレースの JSON（形をテストで固定する）

JSON Schema を `src/semantica_agent/schemas/trace.schema.json` に置き、書き出しのたびに検証する。主なフィールド：

| フィールド           | 内容                                                                                                                                                                            |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `trace_version`      | 形式の版（"1"）                                                                                                                                                                 |
| `session_id`・`turn` | 相談とターン                                                                                                                                                                    |
| `started`・`ended`   | 時刻                                                                                                                                                                            |
| `model`              | 要求したモデルと応答したモデル                                                                                                                                                  |
| `prompt`             | システムプロンプトのパスとハッシュ                                                                                                                                              |
| `ontology`           | `ontology/` のコミットハッシュと未コミットの変更の有無、`schema.ttl` の `owl:versionInfo`                                                                                       |
| `question`           | 職員の発言                                                                                                                                                                      |
| `events[]`           | `{seq, time, type, ...}`。type は `user`・`assistant_text`・`thinking`・`tool_call`・`tool_result`・`answer`。ツールのイベントは引数・結果・`nodes`（触れたノードと状態）を持つ |
| `case`               | 最後の判定に使った事案（Turtle と、項目ごとの状態・値・引用・推測）                                                                                                             |
| `judgment`           | 判定（`reject`・`needsCorrection`・`needsInquiry`・`additionalProcedure`・`acceptable`・`pending`）、暫定の判定、未確認の項目、評価できなかったルール、指摘の一覧               |
| `flow`               | ターンの終わりのフローの状態（業務ごとに、ノードの短い ID → 状態）                                                                                                              |
| `answer`             | 本文と、検証後の主張（種類、ノード、下げた理由）                                                                                                                                |

再生は `events` を先頭から適用して `flow` を作り直すことで行う。最後まで適用した結果が `flow` と一致することをテストで確かめる。

## 7. フローの可視化

### 7.1 フローの形

- 業務ごとに、オントロジーから引く：業務 → 工程（`kos:stepNumber` の順、`kos:nextStep`）→ 項目（`kos:hasItem`・`kos:hasSubItem`、`kos:itemOrder` の順、`kos:itemLabel` と `rdfs:label`）。適用条件（`kos:appliesWhen`）は項目に小さく添える。
- 業務はタブで切り替える。A の質問では出生届を開く。B の質問では、触れたノードがいちばん多い業務を開く。
- 工程・項目に属さないノード（条文、条文の版、改正、書類など）は、フローの横の「参照した法令・ノード」の一覧に出す。

### 7.2 ノードの状態と色

状態はツールの結果からコードが決める（LLM の申告からは決めない）。

| 状態       | 決め方                                                                                                          | 表示         |
| ---------- | --------------------------------------------------------------------------------------------------------------- | ------------ |
| 指摘あり   | 判定の指摘の `kos:implementsCheck` の審査項目。判定の種類で色を分ける（受理不可・補正・照会・追加の手続・参考） | 種類ごとの色 |
| 通過       | ルールのある審査項目で、ルールが評価され（使う入力がそろっている）、指摘が無い                                  | 緑           |
| 評価できず | ルールのある審査項目で、適用されるルールが §5.1.1 で評価できずになった（使う入力に未確認がある）                | 灰の斜線     |
| 人の確認   | 審査項目にルールが無い（オントロジーの仕様 §4.7。子の名の文字など）                                             | 紫の枠       |
| 参照       | ツールの結果に出てきた（B の問い合わせ、`describe_node` など）                                                  | 青の枠       |
| 未到達     | 上のどれでもない                                                                                                | 色なし       |

- 工程の色は、属する項目のうち最も重い状態にする（指摘 ＞ 評価できず ＞ 人の確認 ＞ 通過 ＞ 参照）。
- 「ルールの使う入力」は、各ルールのシェイプ（SPARQL の文字列を含む）に現れる事案側のプロパティを、起動時にコードが洗い出して決める。ルールごとの期待する入力の集合はテストで固定する（ルールを変えたら気づけるように）。
- 1 つの審査項目に複数のルールが付くとき（続き柄・嫡出には手順書時点・現行・差分の 3 つ）、色は**出生日で適用される版のルール**の結果だけで決める（設計者の判断）。適用されない版のルールは状態に数えない。判定の種類が参考（`kos:Info`）の指摘（手順書時点のルールの比較用の結論、手順書と現行で結論が違うこと）は、色を変えず「参考」の印として添える。
- 版の切り替え（出生日で選んだ版）は、審査項目に「手順書時点」「現行（2024-04-01）」の印で出す。暫定（未承認の現行版）の指摘には印を付ける。

### 7.3 画面

```
┌ 質問 ───────────────┐┌ AIの処理（イベントの列。押すとその時点の状態を再生）────────┐
│ 4/1生まれ、婚姻150日 ││ ①質問 → ②事案に変換 → ③判定 → ④ノード参照 → ⑤回答           │
│ 父が非本籍地で届出…  │├ 出生届のフロー ［出生｜婚姻｜離婚｜死亡｜交付］─────────────┤
│                      ││ [1.受付]→[2.審査]→[3.入力]→…→[7.送付]                         │
│【判定】追加の手続   ││   ├ 届出地       ● 通過                                       │
│ （ほかに未確認あり） ││   ├ 続き柄・嫡出 ● 通過（現行 772条）［参考］                 │
│ 回答：公用請求が要る ││   ├ 届出期間     ▲ 追加の手続                                 │
│  [ルール] BIRTH-…    ││   ├ 添付書類     ○ 評価できず（出生証明書が未確認）           │
│  [推測]   …          ││   ├ 子の名の文字 ◇ 人の確認                                   │
│ 母の生年月日は？     ││   └ 母の年齢     ○ 評価できず（母の生年月日が未確認）         │
│ 入力の解釈（表）     │├ ノードの詳細：ルール → 審査項目 → 条文の版 → 手順書の原文・e-Gov ┤
└──────────────────────┘└───────────────────────────────────────────────────────────────┘
```

- 処理の進みは Server-Sent Events で送り、イベントが届くたびに色を更新する。
- 「AIの処理」の列のイベントを押すと、そのイベントまでを適用した状態を描く（状態遷移の再生）。
- ノードを押すと詳細を出す：短い ID、ラベル、出典（手順書の PDF の頁・印刷頁・原文、または e-Gov の URL と確認日）、条文と版、ルール、`kos:reviewStatus`。
- 回答の主張は、根拠の種類の印（ルール／事実／推測）と根拠のノードへのリンクを付けて出す。
- 「過去のトレース」から保存した JSON を開き、同じ画面で再生できる。

### 7.4 サーバー（`web.py`）

- `uv run python -m semantica_agent.web` で起動し、`127.0.0.1` だけで待ち受ける（ポートは設定、既定 8765）。
- API（目安。名前と形は実装に任せる）：画面の配信、業務のフローの形、新しい相談、質問の送信（応答は SSE）、ノードの詳細、トレースの一覧と取得。
- 同時に処理する質問は相談ごとに 1 つ。処理中の送信は拒む。

## 8. エラーと境界

- オントロジーの読み込み・整合性の検証に失敗したら、起動を止めて理由を出す。
- SDK のエラー、ツールの例外は、トレースに `error` のイベントとして残し、画面に出す。ターンは失敗として保存する（握り潰さない）。
- `run_sparql` は時間の上限（設定、既定 10 秒）を設ける。
- トークンや環境変数の値をトレース・ログ・画面に出さない。

## 9. テスト

- Unit：引用の照合（空白の違い、別のターンの発言、含まれない引用）、事案の RDF の組み立て（列挙値、型、推測の印、`given`・`none`・`unknown`、複数値の `complete`）、判定の後処理（未確認の項目でルールが評価できずになる、判定保留・受理可・指摘ありの決め方、未確認の書類で照会の指摘が出ない）、主張の検証（下げる場合と下げない場合）、ルールの使う入力の洗い出し（ルールごとの期待値）、フローの状態の決め方（指摘・通過・評価できず・人の確認・参照、工程への集約）、`run_sparql` の拒否（SELECT 以外、SERVICE）、トレースの JSON Schema での検証、再生の一致。
- Integration：本物のオントロジーを読み、各ツールを直接呼ぶ。`judge_birth_case` に `tests/fixtures/birth_cases/cases.json` の事案を JSON に直して渡し、`judge` と同じ判定になる。B の問い合わせで、CQ2 の答えのノードが 4 業務の工程 7 に「参照」として付く。
- Web：FastAPI の TestClient で、SDK の応答をフィクスチャで差し替えたエージェントを使い、SSE のイベントの並びと保存されたトレースを確かめる。
- `llm`：出生届の事案 1 件と問い合わせ 1 件を実際に流し、トレースが Schema に合い、判定が正解表と一致する（既定では流さない）。
- 画面の JS は、描画の元になる状態の計算をサーバー側（Python）に寄せ、JS は描くだけにする（テストを Python で書けるようにするため。設計者の判断）。
- カバレッジは `src/semantica_agent/` で 80% 以上。

## 10. 実装する側に任せること

- システムプロンプトの文面（§4.2 を満たす範囲で）。
- API のパスと SSE のイベント名。
- 画面の色の具体的な値、配置の細部。
- `search_nodes` の一致の仕方（部分一致でよい）。
- `report.md` の書式（トレースの内容を人が読める順に並べる）。
