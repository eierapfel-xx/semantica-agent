# オントロジー設計（戸籍の窓口業務）

- 日付：2026-11-16
- 対象：手順書 → オントロジー（スキーマ・SHACL・インスタンス・判定ルール）の段。エージェントとトレースの形式は次の仕様で決める。
- 入力：`docs/domain/手順書.pdf`（Ver1.0、11 頁。PDF の頁 2〜11 が手順書の印刷頁 1〜10）

## 1. 目的

窓口職員の審査支援エージェントが、届出の内容を受け取って「受理できるか・何が足りないか」を根拠付きで返せるようにする。そのためのオントロジーを作る。このプロジェクトの目的は「オントロジーを持たせることが役に立つか」を検証することで、特に見たいのはトレーサビリティ（結論から、ルール → 審査項目 → 条文 → 手順書の原文まで辿れること）。

### ゴール

- 手順書の表（区分・業務手順・備考の法令）を、5 業務すべてについて工程・作業・審査項目・法令のノードに起こす。
- 出生届は、届出の事案データに判定ルール（SHACL）を当てて、受理可否・不足・照会の要否を出せるようにする。
- 手順書の記述と現行法の違いを、両方ともオントロジー上に持つ。どちらの法の版で判定したかを区別できるようにする。
- すべてのノードに、安定した識別子と出典（手順書の頁と原文、または現行法令の URL）を持たせる。
- competency questions（CQ）を SPARQL で引き、期待する答えが返ることをテストで固定する。

### ゴールにしないこと

- エージェント本体、トレースの JSON スキーマ、報告の形（次の仕様で決める）。
- 出生届以外の 4 業務の判定ルール（出生届で縦に通してから広げる。広げるときに別の仕様を書く）。
- 子の名に使える文字の判定（常用漢字表・人名用漢字表の取り込みが要る）。住所・入る戸籍が実在するかの照合（外部システムが要る）。これらは事案データの入力値として受け取るか、人の確認事項として返す。
- 外国人が当事者になる場合の要件、広域交付など、手順書にない業務。

### 失敗とみなすこと（動いても失敗）

- 手順書に無いことが、出典の無いまま、または手順書が出典であるかのように混ざっている。
- LLM が出した識別子や出典をそのまま信じていて、原文と食い違っても検出できない。
- 現行法と手順書の記述が 1 つのノードに混ざり、どちらで判定したかが分からない。
- 生成をやり直すたびに IRI が変わり、トレースや CQ のテストが壊れる。

## 2. 進め方の選択（Approaches）

| 案            | 内容                                                                         | 長所                                                                                                          | 短所                                               |
| ------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| A             | 骨組み（スキーマ・インスタンス）は LLM で作り、判定ルールと SHACL は人が書く | ルールの正しさを人が担保できる                                                                                | 「LLM で生成する」という方針から外れる部分が大きい |
| **B（採用）** | 判定ルールと SHACL も LLM が下書きし、人がレビューして直す                   | 方針どおり全部を LLM で生成できる。人が直した箇所を記録すれば、LLM の生成がどこまで使えたかも検証の材料になる | レビューと修正の手間、修正の記録が要る             |

**B を採用**（ユーザーの決定）。人が直した箇所は、コミットを分け、ノードの `kos:reviewStatus` にも残す（§6.6）。

### 範囲

- 表の取り込み（工程・作業・審査項目・法令ノード）は 5 業務すべて。分量が少なく、業務をまたぐ CQ（例：「戸籍法施行規則第48条が関わる工程」）に全業務が要るため。
- 判定ルールは出生届から。出生届には、嫡出の判定（条件付き）、届出期間、非本籍地での届出、法改正（民法772条）がそろっている。
- 法改正のノードは、出生届以外の業務の分も作る。影響範囲を辿る CQ に要るため（判定ルールは作らない）。

## 3. 全体の流れ

```
手順書.pdf
  │ (1) 表の取り出し（コード、LLM 不使用）
  ▼
data/extracted/rows.json            … 行ごとの 区分・業務手順・備考・頁・座標
  │ (2) スキーマ生成（LLM：KosekiOntologyGenerator）→ 人のレビュー → 固定
  ▼
ontology/schema.ttl
  │ (3) インスタンス生成（LLM：業務ごと）→ コードで検証・IRI 付与・Turtle 化 → 人のレビュー
  ▼
ontology/instances/*.ttl, ontology/law/laws.ttl
  │ (4) 現行法の情報（LLM の下書き → 人が e-Gov で確認）
  ▼
ontology/law/amendments.ttl
  │ (5) 判定ルール（LLM の下書き → 人のレビュー・修正）
  ▼
ontology/rules/birth-rules.ttl
  │ (6) SHACL 検証・CQ テスト
  ▼
tests/（CQ の期待値）
```

各段の生成物はファイルに残し、次の段はそのファイルを入力にする。

## 4. オントロジーの構成

### 4.1 名前空間とファイル

名前空間はコードの 1 か所（`src/semantica_agent/namespaces.py`）で定数にし、Turtle の `@prefix` と一致させる。

| 接頭辞   | URI                                              | 中身                                                         |
| -------- | ------------------------------------------------ | ------------------------------------------------------------ |
| `kos:`   | `https://semantica-agent.example/koseki/schema#` | クラス・プロパティ                                           |
| `kd:`    | `https://semantica-agent.example/koseki/id/`     | インスタンス（業務・工程・法令・ルール等）                   |
| `kcase:` | `https://semantica-agent.example/koseki/case/`   | 審査の事案データ（エージェントの入力。ファイルには置かない） |

ホスト名は実在しない予約ドメイン（`.example`）にする。公開するときに差し替える。

| ファイル                                                            | 中身                                                             | 作り方                           |
| ------------------------------------------------------------------- | ---------------------------------------------------------------- | -------------------------------- |
| `ontology/schema.ttl`                                               | クラス・プロパティ（業務側と事案側）                             | LLM → レビュー → 固定            |
| `ontology/shapes/integrity.ttl`                                     | オントロジー自身の整合性を見る SHACL（全審査項目に出典がある等） | LLM の下書き → レビュー          |
| `ontology/instances/{birth,marriage,divorce,death,certificate}.ttl` | 業務・工程・作業・審査項目・書類・条件・出典                     | LLM → コードで検証 → レビュー    |
| `ontology/law/laws.ttl`                                             | 法令・条文・条文の版（手順書時点）                               | インスタンス生成と同じ           |
| `ontology/law/amendments.ttl`                                       | 改正と現行版                                                     | LLM の下書き → 人が e-Gov で確認 |
| `ontology/rules/birth-rules.ttl`                                    | 出生届の判定ルール（ルールのノードと SHACL シェイプ）            | LLM の下書き → レビュー・修正    |
| `ontology/provenance.ttl`                                           | 生成の記録（PROV-O）                                             | コードが書く                     |
| `ontology/cq/cqNN.rq`                                               | CQ の SPARQL                                                     | 人が書く（期待値はテスト側）     |

### 4.2 クラス（業務側）

ローカル名は英語、日本語名は `rdfs:label "…"@ja`。下の表は、スキーマ生成のプロンプトに「必ず含める概念」として渡す一覧（§5.3）。定義・上位クラス・補助のプロパティは LLM が埋め、名前はこの表に合わせる。

| クラス                 | ラベル       | 内容・例                                                                                                                                                                                                                          |
| ---------------------- | ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `kos:Business`         | 業務         | 出生届、婚姻届、離婚届、死亡届、戸籍謄本等の交付。区分（「戸籍」）を持つ                                                                                                                                                          |
| `kos:ProcedureStep`    | 工程         | 表の「区分」列。例：1.受付、2.審査、7.届書類の保存、法務局への送付                                                                                                                                                                |
| `kos:StepItem`         | 手順項目     | 「業務手順」列の 1 項目（(1)、①、○、★）。入れ子にできる。下の 2 つの上位クラス                                                                                                                                                    |
| `kos:Task`             | 作業         | 確認以外の作業（例：公用請求で戸籍謄本を入手する、受付番号を発番する）                                                                                                                                                            |
| `kos:ReviewCheck`      | 審査項目     | 「〜か」「〜を確認する」の形の確認（例：届出期間内の届出か）                                                                                                                                                                      |
| `kos:Condition`        | 適用条件     | 項目が当てはまる条件（非本籍地に届出された場合、代理人の場合、協議離婚の場合、未成年者の場合）                                                                                                                                    |
| `kos:DocumentType`     | 書類の種類   | 届書、出生証明書、死亡診断書、本人確認書類、委任状、遅延理由書、父母の同意書、要件具備証明書、母子健康手帳 等                                                                                                                     |
| `kos:RecordItem`       | 記載事項     | 届書に書くべき事項（生まれたとき、生まれたところ、出生時刻、生存配偶者の年齢 等）                                                                                                                                                 |
| `kos:PartyRole`        | 関係者の種類 | 届出人、届出義務者、届出事件本人、来庁者、使者、代理人、法定代理人、証人、第三者、公的機関、特定事務受任者。脚注の定義（例：来庁者＝現に届出の任に当たっている者）も持つ                                                          |
| `kos:Organization`     | 機関         | 法務局、管轄簡易裁判所、本籍地市区町村、妻の従前本籍地市区町村                                                                                                                                                                    |
| `kos:Law`              | 法令         | 戸籍法、戸籍法施行規則、民法、住民基本台帳法、人口動態調査令、母子保健法施行規則、法の適用に関する通則法、墓地、埋葬等に関する法律、地方公共団体の手数料の標準に関する政令。通知・事務連絡（法務省民一第317号）もこのクラスで持つ |
| `kos:LegalProvision`   | 条文         | 条・条の枝番・項・号の単位。例：戸籍法第27条の2第1項                                                                                                                                                                              |
| `kos:ProvisionVersion` | 条文の版     | 条文のある時点の内容。手順書時点の版と現行版                                                                                                                                                                                      |
| `kos:LegalAmendment`   | 改正         | 改正法（法律番号・施行日）。改正する条文を指す                                                                                                                                                                                    |
| `kos:SourceReference`  | 出典         | 手順書の頁・行・原文、または現行法令の URL と確認日                                                                                                                                                                               |
| `kos:JudgmentRule`     | 判定ルール   | 審査項目を事案データで判定するルール。SHACL シェイプを指す                                                                                                                                                                        |
| `kos:DerivedValue`     | 派生値の定義 | 事案データから計算する値（日数・年齢）の定義（§4.6）                                                                                                                                                                              |

`kos:ProcedureStep` から `kos:StepItem` までは、すべて 1 つの業務に属する。業務をまたいで同じ内容の工程（例：「届書類の保存、法務局への送付」）は、業務ごとに別のノードにする。共通性は、同じ条文を参照していることで表す。

### 4.5 SHACL の 2 層

1. **整合性シェイプ**（`shapes/integrity.ttl`）：オントロジー自体の検査。全ノードに `dcterms:identifier` と `kos:hasSource` が 1 つ以上ある。`kos:ReviewCheck` は 1 つの工程に属する。`kos:currentTreatment` が `kos:Changed` か `kos:Obsolete` なら、`kos:citesProvision` の先のどれかに、現行版または廃止の版がある。出典の種類が「推測」なら `rdfs:comment` がある。
1. **判定シェイプ**（`rules/birth-rules.ttl`）：事案データの検査。1 つのシェイプが 1 つの `kos:JudgmentRule` に対応する。`sh:severity` と判定の種類は次のように対応させる。

| 判定の種類（`kos:outcome`） | `sh:severity`  | 意味                                                                     |
| --------------------------- | -------------- | ------------------------------------------------------------------------ |
| `kos:Reject`                | `sh:Violation` | 受理できない                                                             |
| `kos:NeedsCorrection`       | `sh:Violation` | 補正・追完が要る（記入漏れ、書類不足）                                   |
| `kos:NeedsInquiry`          | `sh:Warning`   | 法務局への受理照会が要る                                                 |
| `kos:AdditionalProcedure`   | `sh:Warning`   | 受理できるが追加の手続が要る（遅延理由書、簡易裁判所への通知、公用請求） |
| `kos:Info`                  | `sh:Info`      | 参考（手順書と現行法で結論が違う 等）                                    |

`sh:Violation` を 2 種類に分けるため、判定の種類は `sh:severity` からは読まず、必ず `sh:sourceShape` → `kos:JudgmentRule` → `kos:outcome` で引く。検証結果から、ルール → 審査項目 → 条文の版 → 出典と辿れることが、トレーサビリティの土台になる。

### 4.6 日付の計算（派生値）

「婚姻後200日」「出生後14日以内」のような日付の計算は、SPARQL の日付演算が処理系ごとにばらつくので、SHACL の中ではしない。検証の前にコードで派生値を計算して事案データに足し、ルールは整数を比べる。

- 派生値の定義は `kos:DerivedValue` のノードとしてオントロジーに持つ（名前、計算式の説明、根拠の条文。例：期間の数え方の根拠として戸籍法第43条）。
- 計算するコードは定義ノードの IRI を受け取って計算する。足した値には `prov:wasDerivedFrom`（元の日付）と `prov:wasGeneratedBy`（派生値の定義）を付け、トレースに残す。
- 出生届で使う派生値：`daysFromMarriageToBirth`、`daysFromPrevMarriageEndToBirth`、`filingDeadline`（期間の末日）、`daysLate`、`motherAgeAtBirth`、`childAgeAtFiling`。
- 届出期間の数え方（初日を算入するか、末日が休日のときの扱い）は戸籍法第43条などを e-Gov で確かめてから定義に書く（§6.4 の確認対象）。
- 末日が休日なら延ばす扱いだと確かめられた場合、休日の判定には `jpholiday`（祝日）と固定の表（年末年始 12/29〜1/3）を使う（設計者の判断）。祝日のデータは境界で検証し、対象の年が無ければ止める。

### 4.6.1 法の版の選び方（設計者の判断）

適用する版は、「常に現行」ではなく、事件の発生日（出生届なら出生日）で選ぶ。嫡出推定の改正は、施行日以後に生まれた子に適用される経過措置があるため。

- 各判定ルールは、`kos:underVersion` の版の `kos:validFrom` と `kos:validUntil` に、出生日が入るときだけ適用する。この条件はシェイプの `sh:target`（SPARQL ターゲット）に持たせる。
- 手順書時点のルール（B4a）は、適用される版に関係なく、比較のために常に評価する。結論は `kos:Info` として出し、受理可否には使わない。
- B4c は、「適用される版のルール」と「手順書時点のルール」の結論が違うときに出す。
- テスト用の事案には、2024-03-31 生まれと 2024-04-01 生まれの組を入れる。

## 5. LLM での生成の流れ

### 5.1 表の取り出し（LLM を使わない）

pdfplumber でテキストを取り出すと、「業務手順」と「備考」の 2 列が行の中で混ざる（例：「② 出生届と出生証明書の記載事項と合致しているか確認す 用意する。（戸籍法第29条…」）。このため次のように取り出す。

1. 各頁で、表の見出し（「区分」「業務手順」「備考」）の x 座標から 3 列の境界を決める。罫線が取れる頁は `extract_table` を使い、取れない頁は語の座標で列に振り分ける。
1. 1 行目の「業務名」から業務を、頁をまたぐ表は直前の業務の続きとして判定する。
1. 1 行（PDF 上の 1 行）を 1 レコードにする：`row_id`（`p{PDF頁}-r{行番号}`）、業務名、区分、業務手順の文字列、備考の文字列、PDF の頁、印刷頁、y 座標。
1. 脚注（「1 現に届出の任に当たっている者」など）と頁の上部の注記は、別の種類のレコードにする。
1. 出力は `data/extracted/rows.json`。テストで、各業務の区分の並び（出生は 1〜7、婚姻は 1〜8 等）と、既知の数行の備考が取れることを確かめる（`slow`）。

行の折り返し（1 つの項目が複数行にまたがる）は、ここではまとめない。まとめるのは LLM の仕事にし、どの行を使ったかを `row_id` で返させる（§5.4）。

「※」の注記と、「（〜場合には…照会する。）」のような括弧書きも、独立した `kos:StepItem` にする（設計者の判断）。判定ルールがこれらを指すため（B3・B6・B7・B9・B12、CQ4〜CQ6）。条件の部分は `kos:appliesWhen` の `kos:Condition` に持たせる。親の項目は PDF 上の位置で機械的に決めず、意味から LLM が決めて `parent` で返す（例：学齢の括弧書きは、PDF 上では「生まれたとき」の ○ の下にあるが、親は 2.審査 にする）。決め方に自信が無ければ `"alignment": "uncertain"` を付ける。

### 5.2 Agent SDK のプロバイダー

- `src/semantica_agent/llm_provider.py` に `ClaudeAgentSDKProvider(BaseProvider)` を作り、`provider_registry.register("claude_agent_sdk", ClaudeAgentSDKProvider)` で登録する。
- `generate(prompt)` は `claude_agent_sdk.query` を `ClaudeAgentOptions(allowed_tools=[], max_turns=1, system_prompt=…, model=…)` で 1 回呼び、テキストを返す。semantica 側は同期呼び出しなので、内部で `anyio.run` で包む。
- `generate_structured(prompt)` は、`generate` の結果から JSON を取り出す（`BaseProvider._parse_json`）。取り出せなければ、エラーの内容を付けて 1 回だけ再要求し、それでも駄目なら例外で止める。
- モデルは環境変数 `ONTOLOGY_GEN_MODEL`（未設定なら設定ファイルの既定値）で決める。実際に応答したモデル名は、応答メッセージから取って記録する。
- `ANTHROPIC_API_KEY` があれば起動時に止める（Pro のログインで動かすため）。
- 各呼び出しの、プロンプト全文・応答の生テキスト・モデル・時刻を `data/generation/<run_id>/` に保存する（git 管理外）。

### 5.3 スキーマの生成

- `KosekiOntologyGenerator(LLMOntologyGenerator)` を作り、`_build_prompt` を日本語のプロンプトで上書きする。プロンプトは `src/semantica_agent/prompts/schema.md` にファイルで置き、ハッシュを記録する。
- プロンプトの中身：
  1. 役割：戸籍の窓口業務の審査支援に使うオントロジーを設計する。
  1. 入力：手順書の全業務の行（`rows.json`）。
  1. 必ず含める概念：§4.2 のクラス表、§4.3・§4.4 のプロパティ表（名前を固定）。
  1. 命名の規則：クラスは UpperCamelCase、プロパティは lowerCamelCase の英語。日本語は label に書き、説明は comment に書く。
  1. 出力：semantica の JSON 形式（classes / properties）に `label_ja`、`comment_ja` を足したもの。
  1. 手順書に無い概念を足すときは、`"speculative": true` と理由を付ける。
- `_normalize_output` は `label_ja` と `comment_ja` を落とさないよう上書きする。Turtle への変換は、自前の rdflib のコードで行う。semantica のルールベースの生成機能は名前を正規化してしまうので使わない（CLAUDE.md の「よくある落とし穴」）。
- スキーマを生成する前に、§4.7 の全ルールが使う事案側のプロパティを洗い出し、§4.4 の表と突き合わせる（計画の最初のタスク）。足りなければこの仕様を改訂してから生成する。スキーマを固定したあとで足りないものが見つかったら、仕様を改訂して確認を取る。
- 生成後、コードで、表の名前が全部あるか、余分な名前がないかを照合し、差分をレビュー用に出す。人が直して固定したら、以降の生成はこの `schema.ttl` を入力にする。スキーマを変えるときは、この仕様を改訂する。

### 5.4 インスタンスの生成（業務ごと）

- 入力：その業務の `rows.json` の行、固定した `schema.ttl` の要約（クラス・プロパティとラベル）、既にある法令ノードの一覧。
- プロンプトは `src/semantica_agent/prompts/instances.md`。指示の中身：
  1. 区分ごとに工程を、業務手順の (1)・①・○・★ ごとに項目を作る。複数行にまたがる項目は 1 つにまとめる。
  1. 項目ごとに、作業か審査項目か、適用条件、必要書類、記載事項、関係者、照会・通知の先を埋める。
  1. 備考の法令は、条文ごとに `{law, article, branch, paragraph, item}` に分ける。略称（住基法）は正式名にし、明らかな誤記（「第27条2」→ 第27条の2）は直して `normalization_note` に書く。条文でない備考（「記入例を用意する」など）は `notes` に入れる。
  1. 各項目に、使った行の `row_id` の一覧と、原文の引用（行のテキストの部分文字列）を付ける。
  1. 備考の法令がどの項目に対応するかは、行の y 座標の近さで判断し、自信が無ければ `"alignment": "uncertain"` を付ける。
  1. 手順書に無いことは書かない。書く必要があれば `"speculative": true` と理由を付ける。
- 出力の JSON は、IRI を含めない。IRI はコードが付ける（§7.1）。
- コードでの検証（失敗したらその業務を止め、理由を出す）：
  - 引用が、指定した `row_id` の行のテキストに、空白を除いて含まれている。
  - 条文の各要素が、その行の備考のテキストに現れる（正規化の注記があるものを除く）。
  - 全部の行が、どれかの項目か注記に使われている。使われなかった行は一覧にして止める。
  - スキーマに無いクラス・プロパティを使っていない。
- 出典（`kos:SourceReference`）は、LLM の出力ではなく、`row_id` から行のレコードを引いてコードが作る。頁・行・原文は LLM に頼らない。

### 5.5 現行法の情報

- 改正の一覧（§6.2）を入力に、LLM が改正のノードと現行版の要約を下書きする。
- Claude が e-Gov（法令 API か条文のページ）から該当の条文を取ってきて、下書きに条文の引用・取得元の URL・取得日を付ける（ユーザーの決定）。
- 人は、引用と下書きを照らして承認する。承認したら `kos:HumanReviewed` にし、確認日と確認者を出典に書く。承認までは `kos:LlmDraft` のまま置く。後の段の作業（ルールの下書き、テスト）は承認を待たずに進めるが、エージェントは `kos:LlmDraft` の現行版を判定に使わない（ルールで止める）。
- 出生届のテスト用の事案の「正しい判定」（手順書時点と、適用される版のそれぞれ）も同じ進め方にする。Claude が条文の引用を付けて正解表を下書きし、人が承認する（ユーザーの決定）。承認前の正解表に基づくテストは、承認のコミットまでは通っても確定扱いにしない。

### 5.6 判定ルールの生成

- 入力：§4.7 の表、出生届のインスタンス、条文の版、事案側のスキーマ、派生値の定義。
- プロンプトは `src/semantica_agent/prompts/rules.md`。出力は Turtle（`kos:JudgmentRule` と SHACL シェイプの組）。SHACL Core で書けるものは Core で書き、条件の組み合わせが要るもの（B4 等）は SHACL-SPARQL（`sh:sparql`）を使う。
- 検証：pyshacl でシェイプとして読めること、§9 のテスト用の事案（各ルールに当たる例と当たらない例）で期待どおりに判定されること。
- 人が直したら `kos:reviewStatus kos:HumanEdited` にし、直したことと理由を `rdfs:comment` とコミットに残す。

### 5.7 保存とレビューの手順

1. 生成は 1 段ずつ CLI（`uv run python -m semantica_agent.build <段>`）で行う。段ごとに `run_id` を振る。
1. Turtle は、差分を読みやすくするために、並びを決まった順にして書き出す（主語の IRI 順、1 行 1 述語）。
1. 生成の記録を `ontology/provenance.ttl` に PROV-O で追記する：`prov:Activity`（run_id、段、開始・終了時刻）、`prov:used`（入力ファイルのハッシュ、使った PDF の頁、プロンプトのパスとハッシュ）、`kos:model`（応答したモデル名）、生成したファイル。各ノードからは `prov:wasGeneratedBy` で Activity を指す。
1. LLM の生成結果は、そのまま `ontology/generated/<段>/` に置いて 1 つのコミットにする（`feat: …を LLM で生成`）。テストはこの場所を読まないので、commit-guard のテストは落ちない。レビューと修正を済ませたものを `ontology/` の所定の場所に置き、別のコミットにする（`fix: …を手で修正（理由）`）。手の修正は `diff ontology/generated/<段>/x.ttl ontology/<所定>/x.ttl` で読める（設計者の判断）。
1. レビューで見ること：
   - 行の使い残し・引用のずれの報告が空になっている。
   - `alignment: uncertain` の項目について、条文の対応を原文の PDF で確かめた。
   - 推測のノードの一覧と理由に納得できる。
   - 整合性シェイプによる SHACL 検証が通る。
   - CQ のテストが通る。
1. 生成をやり直したときは、前回の Turtle との差分を見る。IRI はコードが決めるので（§7.1）、内容が同じなら差分は出ない。

## 6. 手順書と現行法の違い

### 6.1 持ち方

```
kd:law/minpo/art/733  (kos:LegalProvision 民法第733条)
  ├─ kos:hasVersion → kd:law/minpo/art/733/version/manual   (kos:Manual, 手順書時点の版)
  └─ kos:hasVersion → kd:law/minpo/art/733/version/2024-04-01 (kos:Repealed, validFrom 2024-04-01)
                          ↑ kos:producesVersion
kd:amendment/R4-102  (kos:LegalAmendment 令和4年法律第102号, effectiveDate 2024-04-01)
  └─ kos:amends → kd:law/minpo/art/733, kd:law/minpo/art/772, …

kd:marriage/step/2/item/4  (審査項目「女性は待婚期間ではないか」)
  ├─ kos:citesProvision → kd:law/minpo/art/733
  ├─ kos:currentTreatment → kos:Obsolete
  └─ kos:currentTreatmentNote "2024年4月1日に再婚禁止期間が廃止された。"@ja
```

- 条文のノードは 1 つで、IRI は版によらず変えない。版は別のノードにする。手順書が参照しているのは条文のノードで、どの版かは判定ルールの `kos:underVersion` で表す。
- 審査項目は手順書の記述のまま残す（消さない）。現行での扱いは `kos:currentTreatment` と注記で表す。
- 判定ルールは、法の版ごとに別のノードにする（B4a と B4b）。エージェントは、事件の発生日に適用される版のルールで判定し（§4.6.1）、手順書時点のルールと結論が違えば `kos:Info` で知らせる。

### 6.2 対象にする改正（下書きの入力。人が e-Gov で確かめる）

| 改正                                                 | 施行日     | 影響する条文                                                                                           | 影響する審査項目                                      |
| ---------------------------------------------------- | ---------- | ------------------------------------------------------------------------------------------------------ | ----------------------------------------------------- |
| 成年年齢の引き下げ（平成30年法律第59号）             | 2022-04-01 | 民法731条（婚姻年齢を男女とも18歳に）、民法737条（未成年者の婚姻の父母の同意。削除）                   | 婚姻 審査②（婚姻年齢、父母の同意書）                  |
| 嫡出推定・再婚禁止期間の見直し（令和4年法律第102号） | 2024-04-01 | 民法772条（婚姻前に懐胎し婚姻後に生まれた子も夫の子と推定、再婚後の夫の推定が優先）、民法733条（削除） | 出生 審査「続き柄・嫡出子か」、婚姻 審査④（待婚期間） |
| 離婚後の共同親権の導入（令和6年法律第33号）          | 2026-04-01 | 民法819条（父母の双方または一方を親権者に）、民法765条（親権者の定めに関する受理要件）                 | 離婚 審査⑤（親権者の指定の遺漏）                      |

- 法律番号・施行日・条文の内容は、上の表も含めて確認の対象にする。確かめるまでは `kos:LlmDraft` として扱う。
- ほかにも手順書の記述に影響しそうな改正（届書・証人の押印義務の廃止、氏名の振り仮名の記載、戸籍証明書の広域交付など）は、LLM に候補を出させる。人が確かめたものだけ追加する。

### 6.3 出典の種類

| 出典の種類（`kos:sourceKind`） | 使う場面                                         | 出典に持つもの                                       |
| ------------------------------ | ------------------------------------------------ | ---------------------------------------------------- |
| `kos:ManualSource`             | 手順書から起こしたもの                           | PDF の頁、印刷頁、業務名、区分、`row_id`、原文の引用 |
| `kos:CurrentLawSource`         | 手順書に無い現行法の情報（改正、期間の日数など） | e-Gov の URL、条文、確認日、確認者                   |
| `kos:Speculation`              | どちらでもない推測                               | 理由（`rdfs:comment`）。仕様書にも理由を書く         |

出生届の届出期間「14日」は手順書に書かれていない（「届出期間内の届出か」と戸籍法第49条だけ）。このような値は `kos:CurrentLawSource` を出典にして、条文の版の `kos:summary` か派生値の定義に持たせる。

### 6.4 e-Gov で確かめる事項（Claude が下書きし、人が承認する。§5.5）

- §6.2 の 3 つの改正の法律番号・施行日・条文の内容。
- 出生届の届出期間（戸籍法第49条）と期間の数え方（戸籍法第43条）、期間の末日が休日のときの扱い。
- 出生届の届出地（戸籍法第25条・第51条）と届出義務者（第52条）の現行の条文。
- 学齢の定義（学校教育法第17条）。母 50 歳以上での照会は通達によるため、出典は手順書の記述にとどめる。

## 7. 識別子と出典の形

### 7.1 IRI

IRI は LLM に決めさせず、コードが、業務・区分の番号・項目の位置から決める。生成し直しても、内容が同じなら変わらない。

| 種類                                   | IRI の形                                                  | 例                                                             |
| -------------------------------------- | --------------------------------------------------------- | -------------------------------------------------------------- |
| 業務                                   | `kd:{business}`                                           | `kd:birth`（birth / marriage / divorce / death / certificate） |
| 工程                                   | `kd:{business}/step/{区分番号}`                           | `kd:birth/step/2`                                              |
| 項目                                   | `kd:{business}/step/{n}/item/{位置}`                      | `kd:birth/step/1/item/1.2`（受付の (1)②）                      |
| 適用条件・書類・記載事項・関係者・機関 | `kd:condition/{slug}` 等                                  | `kd:document/birth-certificate`                                |
| 法令                                   | `kd:law/{slug}`                                           | `kd:law/koseki-ho`、`kd:law/koseki-ho-kisoku`、`kd:law/minpo`  |
| 条文                                   | `kd:law/{slug}/art/{条}[-{枝番}][/para/{項}][/item/{号}]` | `kd:law/koseki-ho/art/27-2/para/1`                             |
| 条文の版                               | `{条文}/version/{manual \| 施行日}`                       | `kd:law/minpo/art/772/version/2024-04-01`                      |
| 改正                                   | `kd:amendment/{元号略}{年}-{号}`                          | `kd:amendment/R4-102`                                          |
| 出典                                   | `kd:source/manual/{row_id}`、`kd:source/egov/{slug}`      | `kd:source/manual/p3-r14`                                      |
| 判定ルール                             | `kd:rule/{business}/{slug}`                               | `kd:rule/birth/legitimacy-current`                             |
| 派生値                                 | `kd:derived/{slug}`                                       | `kd:derived/days-from-marriage-to-birth`                       |

- 項目の位置は、手順書の番号の並び（(1) → 1、① → 1）から決める。番号の無い「○」「★」は、同じ親の中の出現順で振る。
- slug（法令名の英字表記、書類名の英字表記など）は、対応表を `src/semantica_agent/` の定数にする。LLM が対応表に無い名前を出したら止めて、人が表に足す。
- 条文は、手順書が項まで書いていれば項のノードを作り、`kos:partOf` で条のノードにつなぐ。「戸籍法第48条」を指す問いで、項のノードも引けるようにする。

### 7.2 短い ID

人とエージェントの回答で使う ID として、`dcterms:identifier` を全ノードに持たせる。例：`BIRTH-S2-I05`、`LAW-MINPO-772`、`RULE-BIRTH-LEGITIMACY-CURRENT`、`SRC-P3-R14`。IRI と 1 対 1 で、コードで相互に変換できる。

### 7.3 トレースで使う情報

次の段のトレースは、ノードについて次を記録できればよい。どれも上の形で引ける。

- ノードの IRI と短い ID、`rdfs:label`。
- 出典のノード：種類、頁・`row_id`・原文の引用、または URL と確認日。
- 生成の記録：`prov:wasGeneratedBy` の Activity（プロンプトのハッシュ、モデル、入力の頁）と `kos:reviewStatus`。
- オントロジーの版：`ontology/` の git のコミットハッシュ（トレースの側で記録する）と、`schema.ttl` の `owl:versionInfo`。

## 9. テスト

- Unit：表の取り出しの列の振り分け、条文の正規化（略称・枝番・誤記）、IRI の付与、引用・行の検証、派生値の計算（境界：婚姻後 199/200 日、前婚解消後 300/301 日、届出期間の末日とその翌日）、プロバイダーの JSON の取り出し（SDK の応答はフィクスチャで差し替える）。
- Integration：`ontology/` の全ファイルを読み、整合性シェイプによる SHACL 検証が通る。CQ のテストが通る。出生届の判定シェイプを、合成の事案（各ルールに当たる例・当たらない例、嫡出の判定が手順書と現行で分かれる例）に当てて、期待どおりの結果と `sh:sourceShape` → ルール → 審査項目の連鎖が返る。
- `slow`：PDF の全頁を取り出すテスト。
- `llm`：プロバイダーで実際に生成を 1 回流すテスト（小さい入力で）。生成の本番は CLI で行い、テストでは流さない。
- カバレッジは `src/semantica_agent/` で 80% 以上。

## 10. 実装する側に任せること

- 列の境界の決め方（罫線の検出か、見出しの座標か）。
- Turtle の書き出しの並びを決める方法。
- CLI の段の名前と引数。
- プロンプトの文面（§5.3・§5.4・§5.6 の中身を満たす範囲で）。
- slug の英字表記（対応表は定数として 1 か所に置く）。
