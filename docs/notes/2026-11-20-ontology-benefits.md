# オントロジーを使う利点の整理（2026-11-20）

「概念と関係はシステムプロンプト＋RDB でも書ける」「SHACL のルールは Dify などのワークフローで LLM＋プログラムを書けば済む」という問いへの整理。結論から書く。

## 結論

- 技術として、オントロジーや SHACL でしかできないことはほぼ無い。RDB とプログラムで同じものは作れる。
- 利点の正体は「LLM が賢くなる」ことではなく、**ルールをプログラムの中の `if` で終わらせず、名前（ID）と根拠の付いたデータとして外に出すこと**。
- そうすると、判定の結論から「どのルールで、どの法令の、どの版に基づくか」を ID で辿れる。これはこのリポジトリの検証目的（トレーサビリティ）と合う。
- RDF・SHACL はそのための標準的な手段の 1 つで、ルール表・条文の版の表を RDB に作っても同じ考え方は実現できる。

## 「データで持てる」の意味

### 身近な例：駐車場の料金

**A. プログラムに書く**

```python
def fee(hours):
    if hours <= 1:
        return 300
    return 300 + (hours - 1) * 200
```

**B. 料金表を作り、プログラムは表を読むだけにする**

| ルール ID | 条件            | 料金   | 根拠              | いつから   | いつまで   |
| --------- | --------------- | ------ | ----------------- | ---------- | ---------- |
| R1        | 最初の 1 時間   | 300 円 | 2024 年の料金改定 | 2024-04-01 | —          |
| R2        | 以降 1 時間ごと | 200 円 | 2024 年の料金改定 | 2024-04-01 | —          |
| R0        | 1 時間ごと      | 250 円 | 開業時の料金      | 2020-01-01 | 2024-03-31 |

「3 時間でいくら？」の答えはどちらも 700 円で、計算の結果は同じ。違いは計算以外のことを聞かれたときに出る。

| 聞かれること                          | A（プログラム）                | B（表）                                 |
| ------------------------------------- | ------------------------------ | --------------------------------------- |
| この 700 円の内訳は？                 | プログラムを読める人が説明する | 「R1 と R2 を使った」と ID で答えられる |
| その料金の根拠は？いつから？          | コメントがあれば分かる         | 表の列に書いてある                      |
| 2023 年に停めた人の料金は正しかった？ | 古い料金はコードから消えている | R0 の行が残っている                     |
| 料金改定の影響を受けるのはどれ？      | コードを読んで探す             | 「根拠＝2024 年の料金改定」で検索する   |

A では、ルールは分岐にすぎず、名前も根拠も期間も持たない。B では、ルールが ID 付きの行になるので、指さす・検索する・根拠や期間とつなぐ・古い版を残す、ができる。

### このリポジトリでの形

嫡出の判定は、ルールと条文の版を次のように持つ（`ontology/rules/birth-rules.ttl`、`ontology/law/amendments.ttl`。表の形に簡略化）。

| ルール                          | 審査項目（`implementsCheck`）  | 根拠の条文の版（`underVersion`）           |
| ------------------------------- | ------------------------------ | ------------------------------------------ |
| `RULE-BIRTH-LEGITIMACY-MANUAL`  | `BIRTH-S2-I5` 続き柄・嫡出子か | `LAW-MINPO-772-VMANUAL`（手順書の時点）    |
| `RULE-BIRTH-LEGITIMACY-CURRENT` | `BIRTH-S2-I5` 続き柄・嫡出子か | `LAW-MINPO-772-V20240401`（2024 年改正後） |

| 条文の版                  | `validFrom` | `validUntil` |
| ------------------------- | ----------- | ------------ |
| `LAW-MINPO-772-VMANUAL`   | —           | 2024-04-01   |
| `LAW-MINPO-772-V20240401` | 2024-04-01  | —            |

判定の中身（婚姻から 200 日を数える等）は SHACL シェイプ（`kos:shape`）と Python（`review/derive.py`）にあり、データにしても計算は計算として残る。データとして外に出したのは、ルールの名前・どの審査項目のためか・どの法令のどの版に基づくか・いつ有効か、というルールの周りの情報である。

### 3 つの場面での違い

| 場面                                           | プログラムに書いた場合                                               | データとして持った場合                                                                                     |
| ---------------------------------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 職員が「この判定の根拠は？」と聞く             | どの分岐を通ったかは外から見えない。LLM に説明させると作文になりうる | 使ったルールの ID と、その根拠の条文の版を返せる。トレースに ID が残る                                     |
| 法改正で「どこを直す？」                       | 772 条に関わる `if` をコードから探して書き換える。古い条件は消える   | 新しい版の行とルールを足し、古い版に `validUntil` を入れる。「772 条に依存するルール」は問い合わせで引ける |
| 「去年の届出は当時の法律で正しく判定された？」 | 当時のコードを git の履歴から探す                                    | 古い版とルールが残っているので、出生日からその日に有効だった版のルールが選ばれる                           |

## 実際の 1 回の実行で見えたこと

`.archify/flow-replay-20261119-212500/flow-replay.html`（2026-10-20 生まれの子の出生届、届出は 11-10、B 市）で、上の利点が実際に働いた箇所。

- **版の選択がデータで行われた**：2024 年改正後の出生なので、`RULE-BIRTH-LEGITIMACY-MANUAL` は版の `validUntil` を読んだ結果「適用外」になった。コードに日付の `if` は無い。
- **ID で主張を検証できた**：Claude は「評価できず」のルール（`RULE-BIRTH-FILING-PLACE` など）を根拠に `rule` の主張を 3 件出した。`verify_claims` が「この判定で評価したルール・審査項目の ID」と照合し、合わないので推測に下げた。ルールに ID があるから照合できた。

## パランティアのオントロジーとの関係

パランティアの公式資料（Foundry / AIP）が強調する利点は次のとおりで、重点はこのリポジトリと違う。

1. 散らばったデータソースを、オブジェクト・リンクという業務の言葉でまとめる（組織のデジタルツイン）。
1. 名詞（オブジェクト）だけでなく動詞（アクション＝業務操作）を持ち、データを書き戻して業務を動かす。
1. AI が操作してよい範囲をオントロジーで縛る。多くは AI が「提案」を作り、人が承認する。
1. 信頼できるデータ源として LLM に引かせ、幻覚を減らす（推論力が上がるのではなく、正しいデータと決まった処理を道具として渡す）。
1. いつ・どの版のデータの上で・どのアプリから判断したか（decision lineage）を記録する。

このリポジトリと重なるのは 4 と 5。パランティアの中心は 2 と 3（業務を動かすことと権限の統制）で、このリポジトリのオントロジーは参照と判定だけでアクションを持たないため、そこはまだ試せていない。パランティアの資料は「オントロジーはセマンティックレイヤーではない」とも書いており、RDF/OWL のオントロジーとは別物と考えた方がよい。これらはベンダー自身の説明で、第三者の検証ではない。

## 費用と、検証で確かめること

- 費用：学習コスト、ツールの少なさ、LLM は SQL より SPARQL を書き間違えやすい、SHACL で表せない計算（日付の計算など）は結局コードに書く。
- 検証では、比べる相手に「システムプロンプト」だけでなく「同じ内容の RDB＋SQL ツール」も入れると、RDF 固有の利点が残るかを公平に見られる。差が出そうなのは、法改正の影響範囲、業務をまたいだ問い、根拠の示しやすさ。

## ルールは自然言語で書くのか

上の駐車場の料金表の「条件」列は、読みやすさのために日本語で書いたが、実際にプログラムが読む表は次のように値で持つ。

| ルール ID | 何時間目から | 何時間目まで | 1 時間の料金 | いつから   | いつまで   |
| --------- | ------------ | ------------ | ------------ | ---------- | ---------- |
| R1        | 1            | 1            | 300          | 2024-04-01 | —          |
| R2        | 2            | —            | 200          | 2024-04-01 | —          |
| R0        | 1            | —            | 250          | 2020-01-01 | 2024-03-31 |

自然言語で「最初の 1 時間は 300 円」と書くだけなら、システムプロンプトと変わらない。違いは、**条件がプログラムで実行できる形で書かれていること**にある。

このリポジトリの出生届の届出期間のルール（`RULE-BIRTH-FILING-PERIOD`）は、次の 4 つの層でできている。

| 層           | 中身                                                                                                                      | 書き方                       | 誰が使うか                                      |
| ------------ | ------------------------------------------------------------------------------------------------------------------------- | ---------------------------- | ----------------------------------------------- |
| 計算の決まり | `derived/birth-filing-period`：`periodDays 14`、`countFirstDay true`、`extendOnHoliday true`                              | 型の付いた値                 | `review/derive.py` が読んで遅れた日数を計算する |
| 判定の条件   | `shape/birth/filing-period`：`sh:path kos:daysLate ; sh:maxInclusive 0`（遅れた日数が 0 以下でなければ指摘）              | SHACL（複雑な条件は SPARQL） | pyshacl が実行する                              |
| つながり     | `implementsCheck`（審査項目 `BIRTH-S2-I11`）、`outcome`（追加の手続き）、`citesProvision`（戸籍法49条・地方自治法4条の2） | ノードの ID                  | 判定の後処理・トレース・問い合わせ              |
| 説明         | `rdfs:label`「届出期間を過ぎた届出」、`sh:message`、`rdfs:comment`                                                        | 自然言語                     | 人と LLM が読む。判定には使わない               |

自然言語の部分（説明）は表示のためにあり、判定はそれ以外の 3 層だけで決まる。

- **システムプロンプトの場合**：「出生届は出生日を含めて 14 日以内、末日が休日なら翌開庁日」と書き、LLM が読んで、期限内かを自分で計算して判断する。
- **このリポジトリの場合**：プログラムが 14・初日算入・休日延長の値から遅れた日数（8 日）を計算し、SHACL がその値を条件と照らして、ルールの ID 付きで指摘を出す。LLM は期限内かどうかを判断しない。同じ入力なら毎回同じ結果になる。

違いは「誰が実行するか」にある。プロンプトは LLM が解釈して実行し、オントロジーのルールはプログラムが実行する。

SHACL でなければできないわけではない。Python の関数と RDB の表でも同じことはできる。SHACL にした利点は、条件そのものもルールの ID や根拠と同じグラフに置けることで、費用は、条件を書くのが難しいこと（日付の計算は SHACL で書けず Python に出した）。

## 概念と関係：システムプロンプトとの違い

システムプロンプトは LLM だけが読む文章で、解釈は LLM に任される。オントロジーの概念と関係は ID の付いた部品で、LLM もプログラムも同じものを使い、必要な部分だけを検索で取り出せる。

### 身近な例：会社の組織

**A. システムプロンプトに文章で書く**

```
営業部の部長は田中さんです。佐藤さんと鈴木さんは営業部の課長で、
佐藤さんは東京支店長も兼ねています。経理部の部長は別の佐藤さんです。…（300 人分）
```

**B. 組織表にする**

| 人の ID | 名前 | 所属   | 役職 | 上司 |
| ------- | ---- | ------ | ---- | ---- |
| P001    | 田中 | 営業部 | 部長 | —    |
| P002    | 佐藤 | 営業部 | 課長 | P001 |
| P003    | 鈴木 | 営業部 | 課長 | P001 |
| P101    | 佐藤 | 経理部 | 部長 | —    |

| 聞かれること                     | A（文章）                                              | B（表）                             |
| -------------------------------- | ------------------------------------------------------ | ----------------------------------- |
| 佐藤さんの上司は？               | どちらの佐藤さんか LLM が推測する                      | P002 と P101 は別人として区別される |
| 田中さんの下にいる人を全員       | 300 人分の文章から LLM が拾う。漏れても気づけない      | 上司の列を辿れば毎回同じ全員が返る  |
| この答えはどこに書いてあった？   | 文章のどこかとしか言えない                             | 「P002 の行」と ID で示せる         |
| 給与計算のプログラムも組織を使う | 文章はプログラムに読めず、別に表を作る。2 か所がずれる | 同じ表を読む                        |

### このリポジトリでの違い

オントロジーには、業務 5、工程 34、審査項目 86、条文の版 95、手順書への出典 305、届出人の資格 18 種類、書類の種類 19 種類があり、全体で約 1 万トリプル。

1. **言葉の揺れを ID で固定する**。`judge_birth_case` の「届出人の資格」欄は、オントロジーにある資格の ID からしか選べない（入力の JSON スキーマをオントロジーから作る：`review/case_input.py` の `input_schema`）。実際の実行でも Claude は「父が…出しに来ました」を `ROLE-FATHER` にして渡し、SHACL はこの ID で照合した。LLM が最初に生成した判定ルールは日本語のラベルで照合していて黙って空振りしており、IRI での照合に直した（`docs/notes/2026-11-16-ontology-generation.md`）。
1. **LLM とプログラムが同じ定義を使う**。ツールの入力の選択肢、SHACL の判定、トレースと報告のノード ID、`search_nodes`・`describe_node` が引く情報が、すべて同じ定義から来る。プロンプトに書くと、プログラム用に別のコピーが要り、ずれていく。
1. **量が多くても必要な分を漏れなく取り出せる**。「戸籍法施行規則第48条が関わる工程はどれか」は、条文 → 審査項目 → 工程 → 業務を問い合わせで辿り、毎回同じ全件が返る。文章を全部渡して LLM に探させると、見落としに気づけず、聞くたびに件数が変わりうる。
1. **事実の根拠を ID で示せる**。`fact` の主張にはノードの ID を付けさせ、`verify_claims` が「このターンでツールが返したノード」に含まれるかを確かめ、含まれなければ推測に下げる。

システムプロンプトが向くのは、量が少なく変わらず厳密さが要らない知識（振る舞いの指示など）。プロンプトには「どう振る舞うか」、オントロジーには「何が正しいか（業務の知識）」を置くと分けるのがよい。

再生した 1 回では Claude は `search_nodes`・`describe_node` を使っておらず、概念と関係が効いたのはツールの入力の選択肢と SHACL の判定というプログラム側だった。LLM が自分で概念を辿る場面で効くかは、まだ確かめていない。

## 既存の DB がある場合：システムプロンプト＋RDB との違い

比べる相手を「システムプロンプト＋すでにある RDB」にすると、ID で区別する・プログラムと共有する・漏れなく取り出す、は RDB でもできるので差ではなくなる。残る差を整理する。

### 既存の DB に入っているもの、入っていないもの

業務システムの DB は業務を回すために作られている。

```
t_todoke（届出）
  todoke_no | shubetsu_cd | uketsuke_dt | todokenin_kbn | shussho_dt | honseki_cd | …
  20261110-007 | 01 | 2026-11-10 | 1 | 2026-10-20 | 13201 | …

m_code（コード表）
  code_type      | code | name
  todokenin_kbn  | 1    | 父
```

- 入っている：個々の届出の事実（受付日、出生日、届出人など）。
- 入っていない：列の意味（`shussho_dt` が子の出生日であること）、審査の知識（14 日以内、初日算入、休日延長）、根拠（戸籍法49条、手順書のページ、改正の版）。

既存の DB には事実はあっても、意味と知識が無いのが普通で、どこかで補う必要がある。

### 3 つの構成

| 構成                            | 意味と知識の置き場所                                          |
| ------------------------------- | ------------------------------------------------------------- |
| A. システムプロンプト＋既存 DB  | プロンプトに文章で書く                                        |
| B. 既存 DB に知識の表を足す     | ルール表・条文の版の表・列の説明の表を RDB に追加する         |
| C. オントロジーを DB の横に置く | 意味と知識をオントロジーに持ち、DB の列とはマッピングでつなぐ |

「この届出は期限内か。根拠は？」で比べると：

- **A**：LLM が SQL で出生日と受付日を取り、期限と遅れた日数を自分で計算する。根拠の「戸籍法49条」はプロンプトの文章の言い直しで、ID で示せない。改正でプロンプトを書き換えると古い基準は消える。DB の事実は正確でも、解釈の部分が LLM の読み方に頼る。
- **B**：届出期間のルール表（日数・初日算入・休日延長・根拠条文の版・有効期間）を作れば、C とほぼ同じことができる。ただし、既存の業務 DB に表を足せないことが多い（本番 DB の変更の審査、ベンダーの管理）。列の意味を表に持たせると、表の構造を説明する表が要り、オントロジーを RDB の中に手作りすることになる。
- **C**：DB の事実をマッピングで概念（`kos:childBirthDate` など）に置き換え、期間の計算はプログラムがオントロジーのノード（`derived/birth-filing-period`）を読んで行う。根拠は条文の ID で示せる。業務 DB には手を入れない。

| 観点                                   | A. プロンプト＋DB        | B. DB に知識の表                 | C. オントロジー＋DB             |
| -------------------------------------- | ------------------------ | -------------------------------- | ------------------------------- |
| 事実（届出の中身）                     | DB                       | DB                               | DB                              |
| 列の意味                               | プロンプトの文章         | 表に書けるが置き場所の設計が要る | マッピング                      |
| ルールと根拠                           | プロンプトの文章         | 表                               | ノード                          |
| 根拠を ID で示す                       | できない                 | できる                           | できる                          |
| 法改正の版を残す                       | 書き換えで古い版は消える | できる                           | できる                          |
| 既存の DB の変更                       | 不要                     | 必要（現実の壁）                 | 不要                            |
| 手順書・法令など DB の外の知識とつなぐ | 文章で並べるだけ         | DB に取り込む必要がある          | IRI でつなげる                  |
| 費用                                   | 最小                     | DB の変更と設計                  | 別の仕組みの運用と、DB との同期 |

### 結論

- A と C の差は大きい。既存の DB が事実を正確に持っていても、意味・ルール・根拠が LLM の文章の解釈に頼るため、トレーサビリティが弱い。
- B と C の差は小さく、既存の DB に手を入れずに済むこと、DB の外の知識（手順書・法令・その版）を同じ仕組みでつなげること、列の意味（`rdfs:label`・`rdfs:comment`）をデータと同じ形で LLM に引かせられること、が実質的な差になる。
- 既存のデータの上に意味の層を被せるこの形は、既存のデータソースをオブジェクトに対応づけるパランティアのやり方に近い。
- このリポジトリは、このパターンをまだ試していない（既存の DB が無く、届出の事実は Claude が職員の発言から読み取ってツールに渡している）。検証するなら、受付 DB を模した小さなテーブルを用意し、A（プロンプト＋SQL ツール）と C で同じ問いを解かせて、根拠の示しやすさ、日付の計算の正しさ、法改正のケースを比べる。
